# Phenotype System Rules

## Definition

A **phenotype** is a locked, reusable visual and functional identity package for a *class* of people.  
It is never a single named character.

Characters inhabit phenotypes. Phenotypes do not belong to characters.

## What every phenotype must define

1. **Visual ceiling** — exact clothing, armor, marks, and gear that are allowed
2. **Equipment floor** — the minimum items that must be present for the identity to read correctly
3. **Exclusions** — what is forbidden (this is as important as what is allowed)
4. **Social signal** — what the appearance communicates to other characters and to the audience
5. **Behavioral expectation** — how people wearing this phenotype are expected to move, speak, and decide
6. **Transition rules** — when and how a character can move from one phenotype to another
7. **Season / access gate** — when this phenotype becomes available in the story

## Creation gate (same rigor as character creation)

A new phenotype becomes CANON only after:

1. Clear story / institutional function
2. Relationship to existing phenotypes (especially McCluster hierarchy)
3. Locked visual reference or style sheet
4. Equipment and mark rules
5. Explicit exclusions
6. Owner approval

AI-generated art is concept only until the phenotype document is approved and linked.

## Naming convention

- Institutional: `EI-`, `CFI-`, `SOI-`
- Operator: `PRIME-`, `CO-`
- Civilian / entry: `RS-`, `AC-`
- Adversarial: `ADV-`

Version assets as `ID-name-v01.ext`.

## Hierarchy of authority (visual)

```
Prime / Full Operator
        ↑
Cohort Operator (mission)
        ↑
Security Officer
        ↑
Corporate Fits (employee / candidate)
        ↑
Recruit Student / Academic
```

Executive sits parallel to the top of the corporate track and can override most others in non-mission contexts.

## World-completeness goal

The phenotype set should eventually cover every major role the audience will encounter so that the world feels fully inhabited rather than improvised.
